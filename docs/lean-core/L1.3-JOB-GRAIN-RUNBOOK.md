# L1.3 JOB-grain: migration and backfill runbook

Branch `lean/L1.3-job-grain-ship` (PR into `main`; the original branch `lean/L1.3-job-grain` was rebased onto J3a). One migration (`20261023100000_l13_job_grain_stage_view`, replaces the view
`v_unit_stage_status`, touches no data) and two scripts (`scripts/lean-backfill-job-grain.ts` for jobs that exist, `scripts/lean-publish-job-grain-template.ts` for jobs created from now on). Nothing changes on
production until the script is run with `--apply`: the code reads `job_processes.grain`, which is UNIT on every
existing job. **Swayam runs every production command; the phone hotspot is needed (the office LAN blocks port 51870).**

What the backfill does, per job that has a JOB-grain process (codes 1-11 and 33) still planned per unit:
sets `job_processes.grain = JOB` for those codes (one `backfill.jobGrain` audit row each), then writes a NEW schedule
run version (the app's own reschedule path) with one unit-less plan per such process and every other plan copied
unchanged. The old run is kept, not current. Each unit's work is carried into the collapsed plan (earliest start,
latest finish only if every unit is COMPLETE, IN_PROGRESS when mixed; one `schedule.collapseJobGrain` audit row each).
A process whose units are SUBMITTED / ON_HOLD mixed with others is skipped and reported unless `--force-mixed`.
Delay reasons, overrides and notifications stay on the superseded plans as history (the dry run counts them).
A second run changes nothing.

## A. Rehearse on a restored production dump
1. **Dump** (hotspot): `railway run --environment production --service Postgres -- sh -c 'pg_dump -Fc "$DATABASE_PUBLIC_URL" -f ~/despl-prod-$(date +%Y%m%d-%H%M).dump'`
2. **Restore locally:** `dropdb --if-exists despl_rehearse_l13 && createdb despl_rehearse_l13 && pg_restore --no-owner --no-acl -d despl_rehearse_l13 ~/despl-prod-<stamp>.dump`
3. **Migrate the copy** (from this branch): `DIRECT_URL=postgresql://localhost/despl_rehearse_l13 DATABASE_URL=$DIRECT_URL pnpm prisma migrate deploy`. Expect exactly 1 applied (84 in total on `main` as of 21 Oct: J3a and J4a came first; recount if anything merged since). Then `pnpm prisma migrate diff --from-url "$DIRECT_URL" --to-schema-datamodel prisma/schema.prisma --exit-code` must report no difference.
4. **Baseline (read-only):** per job, current-run plan counts and how many are unit-less:
   ```sql
   select j.job_number, count(*) plans, count(*) filter (where pp.unit_id is null) unitless
   from process_plans pp join schedule_runs sr on sr.id = pp.schedule_run_id join jobs j on j.id = sr.job_id
   where sr.is_current group by 1 order by 1;
   ```
5. **Dry run:** `DIRECT_URL=postgresql://localhost/despl_rehearse_l13 pnpm exec tsx scripts/lean-backfill-job-grain.ts | tee ~/rehearse-l13-dry.log`. Read it: the `target:` line must name the rehearsal DB; per job `plansBefore -> plansAfter`; any `skipped` (mixed) process and why; `delayReasonsOnSuperseded`.
6. **Apply, then dry run again:** `... --apply | tee ~/rehearse-l13-apply.log`, then the dry run: it must say `0 job(s)`.
7. **Verify** (set the tenant first: `select set_config('app.tenant_id','1',false);`):
   - DESPL-320's current run has one unit-less plan per JOB process (12) and the per-unit plans of the other 24 (9 units: 216), 228 in all; the previous run still has its plans and is `is_current = false`.
   - `select count(*) from audit_log where action in ('backfill.jobGrain','schedule.collapseJobGrain')` = 2 x the processes collapsed.
   - `v_unit_stage_status` shows the stage of a JOB process (e.g. stage backed by process 10) on all 9 units.
   - Optional: `pnpm dev` against the copy, `LEAN_FLOOR` off then on: spine, stage sheet, Gantt, Planning department page and `/qc` for DESPL-320.
8. Attach both logs and the SQL output to the PR. Decide with SJ about any `skipped` mixed process before production.

## D. Template for new jobs (after the merge deploys; independent of the backfill)
The published production PV template still says UNIT, so a job created from it gets 9 office plans per process until a version carries `grain = JOB` on codes 1-11 and 33. The script clones the newest PUBLISHED PV version, sets `grain = JOB` on the clone only, checks the clone matches the source in every other column, and publishes it (invariant 9; running jobs keep their pin). Rehearse on the restored dump first (A2), then on production:
1. Dry run: `railway run --environment production --service Postgres -- sh -c 'DIRECT_URL="$DATABASE_PUBLIC_URL" pnpm exec tsx scripts/lean-publish-job-grain-template.ts'`. Check the `target:` line and `to switch UNIT -> JOB`.
2. Apply: same command with `--apply` (add `--actor-user <id>` to name the audit user; default is the first active ADMIN).
3. Dry run again: "Nothing to do".
Note: `cloneVersion` does not copy `evidenceKind` or `includeWhen` (template-copy.ts); the script copies them itself and refuses to publish if the clone differs from the source beyond grain. Anyone cloning a version by hand in the editor loses those two columns until template-copy.ts is fixed.
