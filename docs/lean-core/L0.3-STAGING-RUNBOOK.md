# L0.3 — Staging environment runbook

**Executed:** 11–12 Oct 2026 by the agent through the Railway CLI/API, with Swayam's permission (the 11 Oct classifier block did not recur). The sequence below is the one that actually worked, including two corrections to the first draft.
**Result:** staging at `https://despl-staging-staging.up.railway.app` — `/api/health` 200, `_prisma_migrations` 71 applied / 0 failed, boot guard passes as `despl_web`, `/login` serves. Production untouched (`/api/health` 200, last deploy unchanged).

## What this proves that a local rehearsal cannot
Railway's build, its variable injection, `assertDbRole()` at boot, and the internal `*.railway.internal` host (MERGE-RUNBOOK §6.5). Staging is a **separate environment with its own Postgres and synthetic demo data — never a copy of production data.**

## Rules
- Staging deploys from branch `staging`. To rehearse a migration PR: `git push origin <branch>:staging`, read the staging deploy log (pre-deploy must show the migration applying, boot must reach "Ready"), then merge to `main`.
- No staging cron service; `CRON_SECRET` is unset, so `isValidCronSecret` fails closed and `/api/cron/*` returns 401.
- Seeded accounts (`admin@despl.local`, …) exist with the staging `SEED_PASSWORD`. Never reuse a production password.
- Every database command takes an **inline** URL. Never rely on the repo's `.env`.
- Use Postgres 18 client tools: `PATH="/opt/homebrew/opt/postgresql@18/bin:$PATH"`.
- Passing `--service`/`--environment` explicitly on every Railway CLI call: the working directory's link was `production` before this work, then `staging`. `serviceInstanceUpdate` without `environmentId` updates *every* environment.

## Facts learned (these differ from the first draft)
1. **A fresh database cannot run all 71 migrations until `despl_web` exists.** Six migrations (`20260815120000_v_unit_stage_status`, `20260827040000_v_process_plan_percent`, `20260905020000_operation_ref_family_seq`, `20260908100000_tenant_scoped_status_views`, `20260908120000_grant_status_views_despl_app`, `20260908130000_ist_day_marker_overdue_fix`) `GRANT … TO despl_web`. The first deploy therefore fails at `20260815120000_v_unit_stage_status` with `role "despl_web" does not exist`, with 6 migrations applied. The same role is created by `scripts/provision-db-role.sql`, which also needs `despl_app` from migration 2 — hence provisioning *after* the first (failed) deploy, then resolving.
2. **The seed is a single 180 s transaction.** Run from a laptop over a public proxy it times out (`P2028`) and rolls back cleanly. Run it on Railway's internal network.
3. A Postgres service created with `railway add -d postgres` has **no public TCP proxy** and a generated name (`Postgres-XSEs`); references are `${{Postgres-XSEs.DATABASE_URL}}`.
4. `railway environment edit -s <service> deploy.<key>` reported "No changes to apply"; the Railway GraphQL API (`railway api`) worked.
5. `railway ssh` needs a registered SSH key; not used.
6. `railway add --variables` echoes values to the terminal. Staging secrets only; do not use it for production.

## Steps (as executed)

### 1. Environment, database, service
```bash
railway environment new staging                     # empty — NOT --duplicate
railway add -d postgres                             # image postgres-ssl:18; name it printed: Postgres-XSEs
railway add -s despl-staging -r swayams13/despl-production-tracker --branch staging \
  -v 'DIRECT_URL=${{Postgres-XSEs.DATABASE_URL}}' \
  -v 'DATABASE_URL=${{Postgres-XSEs.DATABASE_URL}}' \
  -v "AUTH_SECRET=$(openssl rand -hex 32)" \
  -v "SEED_PASSWORD=$(openssl rand -base64 18 | tr -d '/+=')"
```
`DATABASE_URL` is the owner URL on purpose for now; the boot guard rejects it (expected).

### 2. Service settings (`railway.json` is not honored; `-e`/serviceId/environmentId are the staging ones)
```bash
railway api 'mutation($sid:String!,$eid:String!,$input:ServiceInstanceUpdateInput!){
  serviceInstanceUpdate(serviceId:$sid, environmentId:$eid, input:$input) }' \
  --var sid=<despl-staging service id> --var eid=<staging environment id> \
  --var 'input={"preDeployCommand":["pnpm prisma migrate deploy"],"healthcheckPath":"/api/health","startCommand":"pnpm start"}'
railway domain --service despl-staging --environment staging
```
`preDeployCommand` takes **one** array element; a two-element array is rejected.

### 3. First deploy — expected failure
Pre-deploy applies 6 migrations then fails with `role "despl_web" does not exist`. `_prisma_migrations` has one unfinished row.

### 4. Temporary public proxy, provision, resolve
```bash
# proxy on staging Postgres only (serviceId = the Postgres service, environmentId = staging)
railway api 'mutation($input:TCPProxyCreateInput!){ tcpProxyCreate(input:$input){ id domain proxyPort } }' \
  --var 'input={"applicationPort":5432,"environmentId":"<staging env id>","serviceId":"<Postgres service id>"}'
# owner URL: postgresql://postgres:<POSTGRES_PASSWORD>@<domain>:<proxyPort>/railway?sslmode=require
export PATH="/opt/homebrew/opt/postgresql@18/bin:$PATH"; U='<owner URL>'

# Target check — must show organizations = 0 and the 6 applied rows; stop otherwise.
psql "$U" -At -c "SELECT current_database(), (SELECT count(*) FROM organizations), (SELECT count(*) FROM _prisma_migrations WHERE finished_at IS NOT NULL);"

psql "$U" -v despl_web_password='<new 48-hex password>' -f scripts/provision-db-role.sql
DATABASE_URL="$U" DIRECT_URL="$U" pnpm prisma migrate resolve --rolled-back 20260815120000_v_unit_stage_status
```
Marking it rolled back is safe: Postgres rolled the failed migration's transaction back (the view does not exist).
After this step, `_prisma_migrations` keeps one `rolled_back_at` row as history; count applied with `finished_at IS NOT NULL AND rolled_back_at IS NULL`.

### 5. Point the app at `despl_web`, redeploy
```bash
railway variables --service despl-staging --environment staging --skip-deploys \
  --set 'DATABASE_URL=postgresql://despl_web:<password>@<postgres private domain>:5432/railway'
railway redeploy -s despl-staging -e staging --from-source -y
```
Pre-deploy applies the remaining 65 migrations; boot reaches "Ready"; `/api/health` 200.

### 6. Seed — inside Railway (one-off pre-deploy)
Set `preDeployCommand` to `["pnpm prisma migrate deploy && pnpm db:seed"]`, redeploy, wait for SUCCESS ("Seed complete: …" in the log), then **set it back** to `["pnpm prisma migrate deploy"]` immediately — otherwise every later deploy reseeds. Result: 1 organization, 20 users, 3 jobs, 9 units.

### 7. Clean up, verify
1. `tcpProxyDelete` the proxy from step 4; discard the owner URL.
2. `curl https://despl-staging-staging.up.railway.app/api/health` → 200 `{"status":"ok"}`.
3. Sign in at `/login` as `admin@despl.local` through the real form (**a human does this** — agents may not enter passwords on a deployed host).
4. `SELECT count(*) FILTER (WHERE finished_at IS NOT NULL AND rolled_back_at IS NULL), count(*) FILTER (WHERE finished_at IS NULL AND rolled_back_at IS NULL) FROM _prisma_migrations;` → 71 / 0.
5. Production `/api/health` → 200.

## Rebuilding staging from nothing
Repeat from step 1, or avoid the failed first deploy: create `despl_web` (`CREATE ROLE despl_web LOGIN PASSWORD '…'`) **before** the first migrate runs — e.g. create the Postgres service and proxy first, add the web service afterwards — then run `provision-db-role.sql` once after the migrations (it only needs `despl_app` for its `GRANT`).

## Troubleshooting
| Symptom | Likely cause |
|---|---|
| Pre-deploy: `role "despl_web" does not exist` | expected on a fresh DB — step 4 |
| Seed `P2028 Transaction not found` | run over a slow link — use step 6 |
| Boot error `connected as "postgres" … superuser` | `DATABASE_URL` still the owner URL |
| `password authentication failed for "despl_web"` | password in `DATABASE_URL` differs from the one given to the provision script |
| `/login` loads, sign-in fails | seed not run, or `SEED_PASSWORD` differs from the service variable |
| Health 503 | pending migrations (read the pre-deploy log) or DB unreachable |
