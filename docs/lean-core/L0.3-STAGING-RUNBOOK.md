# L0.3 — Staging environment runbook

**Written:** 11 Oct 2026 · **Run by:** Swayam (Railway dashboard + terminal) · **Agent:** prepared this file and the `staging` branch only.
**Accept:** staging `/login` serves; `/api/health` 200 with 71 applied / 0 failed; boot log has no `assertDbRole` error; production `/api/health` still 200.

## What this proves that a local rehearsal cannot
Railway's build, its variable injection, `assertDbRole()` at boot, and the internal `postgres.railway.internal` host (MERGE-RUNBOOK §6.5). Staging is a **separate environment with its own Postgres and synthetic demo data — never a copy of production data.**

## Rules
- Staging deploys from branch `staging`. A feature branch with a migration is pushed to `staging` **before** its PR merges to `main` (`git push origin <branch>:staging`); read the staging deploy log; then merge.
- No staging cron service. `CRON_SECRET` stays unset on staging: `isValidCronSecret` fails closed, so `/api/cron/*` returns 401.
- Seeded accounts (`admin@despl.local`, …) exist on staging with `SEED_PASSWORD`. Use a strong one and do not reuse a production password.
- Every `psql`/`pnpm` command below that touches Railway uses an **inline** URL. Never rely on the repo's `.env`, which points at your local DB (or worse).
- Prefix tools with `PATH="/opt/homebrew/opt/postgresql@18/bin:$PATH"` — Homebrew's default is 14 and Railway Postgres is 18.

## Steps

### 1. Environment (Railway dashboard, project `bubbly-forgiveness`)
1. **New Environment → Empty** named `staging`. Not "Duplicate production" — that copies production's variables, including its `DATABASE_URL`.
2. **+ New → Database → PostgreSQL.** Choose **18** to match production (18.6). If the template offers only another major version, stop and note it in `progress.md`.
3. **+ New → GitHub Repo → `swayams13/despl-production-tracker`**, branch **`staging`**. Name the service `despl-staging`.

### 2. Variables on `despl-staging`
| Variable | Value |
|---|---|
| `DIRECT_URL` | `${{Postgres.DATABASE_URL}}` (reference to **staging's** Postgres, not production's) |
| `DATABASE_URL` | **literal** copy of the same owner URL for now (replaced in step 6). Prisma's schema reads `env("DATABASE_URL")`; keep it set so the first deploy fails only at the role guard. |
| `AUTH_SECRET` | `openssl rand -hex 32` — **new**, not production's |
| `SEED_PASSWORD` | strong, e.g. `openssl rand -base64 18` |

Do **not** set `CRON_SECRET`. Set `DATABASE_URL` as a literal, not a reference — an injected reference shadowing it caused trouble on production's first deploy.

### 3. Service settings (dashboard — `railway.json` is not honored)
- Pre-Deploy Command: `pnpm prisma migrate deploy`
- Healthcheck Path: `/api/health`
- Start Command: `pnpm start`
- Networking: **Generate Domain**.

### 4. First deploy — expected result
Deploy runs. Pre-deploy log must show **"71 migrations found"** and apply all 71 (fresh DB). The app then **crashes at boot** with `DATABASE_URL is connected as "postgres" … which is a superuser …` (or the Railway owner role's name). That error is `assertDbRole` working. Any other failure is a real problem — stop and read the log.

### 5. Provision `despl_web` (terminal; the public proxy host/port is staging's own, not production's 51870)
Get the public URL from the staging Postgres service → Variables → `DATABASE_PUBLIC_URL`.

```bash
export PATH="/opt/homebrew/opt/postgresql@18/bin:$PATH"
STG_OWNER_URL='<staging DATABASE_PUBLIC_URL>'
WEB_PW="$(openssl rand -hex 24)"      # save this; it goes into DATABASE_URL in step 6

# Target check — must print an EMPTY database (organizations = 0, applied = 71).
psql "$STG_OWNER_URL" -c "SELECT current_database(), inet_server_addr(),
  (SELECT count(*) FROM organizations) AS organizations,
  (SELECT count(*) FROM _prisma_migrations WHERE finished_at IS NOT NULL) AS applied;"
```

**Stop if `organizations` is not 0.** Production has data; staging must be empty before the seed.

```bash
psql "$STG_OWNER_URL" -v despl_web_password="$WEB_PW" -f scripts/provision-db-role.sql
```

### 6. Point the app at `despl_web`
Set `DATABASE_URL` on `despl-staging` to the **internal** host:
`postgresql://despl_web:<WEB_PW>@postgres.railway.internal:5432/railway`
(database name `railway` unless the Postgres service's `PGDATABASE` says otherwise).

### 7. Seed (terminal — inline variables, from the repo root)
```bash
DIRECT_URL="$STG_OWNER_URL" SEED_PASSWORD='<same as step 2>' pnpm db:seed
```
Runs `prisma/seed.ts` then `scripts/h1-backfill-job-ids.ts`. It is the full demo seed on purpose: `SEED_REFERENCE_ONLY=1` creates no users, so nothing could log in.

### 8. Redeploy and verify
1. Redeploy `despl-staging`. Boot log: no `assertDbRole` error.
2. `curl -s https://<staging-domain>/api/health` → `200 {"status":"ok"}`.
3. Browser: `https://<staging-domain>/login` → sign in as `admin@despl.local` with `SEED_PASSWORD`, through the real form.
4. `psql "$STG_OWNER_URL" -c "SELECT count(*) FILTER (WHERE finished_at IS NOT NULL) AS applied, count(*) FILTER (WHERE finished_at IS NULL) AS failed FROM _prisma_migrations;"` → 71 / 0.
5. Production: `curl -s https://<production-domain>/api/health` → 200 (nothing here should have touched it).

## If something goes wrong
| Symptom | Likely cause |
|---|---|
| Pre-deploy: "No migration found" or P1012 env error | `DIRECT_URL` unresolved reference — check it points at the **staging** Postgres service |
| Boot error persists after step 6 | `DATABASE_URL` still the owner URL, or provisioning ran against the wrong database |
| `password authentication failed for user "despl_web"` | `WEB_PW` in `DATABASE_URL` differs from the one given to `provision-db-role.sql` |
| `/login` loads but sign-in fails | seed not run, or `SEED_PASSWORD` differs from the one used for the seed |
| Health 503 | pending migrations (read the pre-deploy log) or DB unreachable |
